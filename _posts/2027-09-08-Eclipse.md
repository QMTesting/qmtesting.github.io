## Introduction

Selenium WebDriver is one of the most widely used tools for automating web browser testing. If you are beginning a career in software testing or learning test automation for the first time, Selenium with Java and TestNG is an excellent place to start.

This tutorial explains, step by step, how to install and configure **Selenium WebDriver with Java, TestNG, Maven, and Eclipse using a modern 2026 setup**.

The Selenium installation process has become much easier than it was several years ago.

Older Selenium tutorials often tell beginners to:

* download Selenium `.jar` files manually;
* add numerous Selenium JAR files to the Eclipse Build Path;
* download ChromeDriver manually;
* determine which ChromeDriver version matches Chrome;
* add ChromeDriver to the Windows `PATH`;
* configure `webdriver.chrome.driver` in Java code; or
* manually download logging libraries such as SLF4J or Logback.

For a normal Selenium project in 2026, you usually **do not need to do any of these things**.

Instead, this tutorial will use:

* **Java Development Kit (JDK) 25 LTS**

* **Apache Maven**
* **Selenium WebDriver 4.48.0**
* **Selenium Manager**

# What Is Selenium WebDriver?

**Selenium WebDriver** is an open-source browser automation tool.

It allows a program to control a web browser in much the same way a person would.

For example, Selenium can:

* open a browser;
* navigate to a URL;
* click links and buttons;
* enter information into forms;
* select checkboxes;
* interact with dropdown lists;
* read text displayed on a webpage;
* switch between browser windows and tabs;
* interact with alerts;
* upload files;
* take screenshots;
* verify information displayed by an application;
* test applications in different browsers; and
* execute automated regression tests.

A manual software tester might perform a test such as:

> Open the website, enter a username and password, click **Login**, and verify that the dashboard appears.

A Selenium automated test can perform those same browser actions programmatically.

---

# What Selenium Is — and Is Not

It is important for beginners to understand what Selenium actually does.

Selenium is primarily designed for **web browser automation**.

It is commonly used for:

* functional testing;
* regression testing;
* browser compatibility testing;
* automated UI testing;
* repetitive browser testing;
* smoke testing; and
* end-to-end web testing.

Selenium itself is **not**:

* a complete testing framework;
* a test management system;
* an API testing tool;
* a performance or load testing tool;
* a defect tracking system; or
* a reporting platform.

That is why Selenium is normally combined with other tools.

For this tutorial, our automation stack will be:

**Selenium + Java + TestNG + Maven + Eclipse**

Each tool serves a different purpose.

| Tool               | Purpose                                               |
| :----------------- | :---------------------------------------------------- |
| Java               | Programming language used to write the tests          |
| Eclipse            | IDE used to write, organize, run, and debug Java code |
| Maven              | Manages dependencies and builds the Java project      |
| Selenium WebDriver | Controls the web browser                              |
| Selenium Manager   | Automatically manages browser drivers                 |
| TestNG             | Organizes, executes, and reports automated tests      |

---

# What Is TestNG?

**TestNG** is a Java testing framework.

The name originally refers to **Testing Next Generation**.

Selenium performs browser automation, while TestNG provides the structure that turns Selenium code into an organized test suite.

TestNG provides features such as:

* test annotations;
* assertions;
* setup and cleanup methods;
* grouping tests;
* test priorities;
* test dependencies;
* parameterized tests;
* data-driven testing;
* parallel test execution;
* suite configuration;
* test reports; and
* XML-based test-suite management.

For example, TestNG uses the annotation:

```java
@Test
```

to identify a method as a test.

It can also automatically execute setup code before every test:

```java
@BeforeMethod
```

and cleanup code after every test:

```java
@AfterMethod
```

As your Selenium project becomes larger, these features make automated tests easier to organize and maintain.

---

# Why Use TestNG with Selenium?

Selenium and TestNG perform different jobs.

Selenium controls the browser.

TestNG controls the **tests**.

For example:

```text
TestNG
   ↓
Start Test
   ↓
Selenium
   ↓
Open Browser
   ↓
Interact With Application
   ↓
TestNG Assertion
   ↓
Pass or Fail
   ↓
Close Browser
```

TestNG is particularly useful for Selenium because it provides features that become valuable as an automation framework grows.

These include:

* `@BeforeMethod` and `@AfterMethod`;
* `@BeforeClass` and `@AfterClass`;
* `@DataProvider`;
* test groups;
* test priorities;
* parallel testing;
* `testng.xml`;
* test dependencies;
* suite-level configuration; and
* automated test reports.

# Step 9: Why We Will Use Maven

Older Selenium tutorials often tell beginners to download a Selenium ZIP file and manually add dozens of `.jar` files to Eclipse.

That approach is no longer the preferred way to create a normal Selenium Java project.

Instead, we will use **Apache Maven**.

Maven is a Java build and dependency-management tool.

Rather than manually downloading Selenium and TestNG libraries, you tell Maven which libraries your project requires.

This information is stored in:

```text
pom.xml
```

Maven then:

1. reads the dependency information;
2. downloads Selenium;
3. downloads TestNG;
4. downloads the additional libraries they require;
5. stores them locally;
6. adds them to the project's classpath; and
7. makes them available to your Java code.

This makes projects much easier to:

* maintain;
* update;
* share;
* store in GitHub;
* run on another computer;
* build automatically; and
* integrate with CI/CD systems.

The Eclipse IDE for Java Developers includes Maven integration, so you do not have to manually configure Maven inside Eclipse for this tutorial.

```xml

         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0

    <groupId>com.qmstesting</groupId>

    <dependencies>

        <!-- Selenium WebDriver -->
        <dependency>
            <groupId>org.seleniumhq.selenium</groupId>
            <artifactId>selenium-java</artifactId>
            <version>4.48.0</version>
        </dependency>

        <dependency>
            <groupId>org.testng</groupId>
            <artifactId>testng</artifactId>
            <version>7.12.0</version>
            <scope>test</scope>

    <build>

            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-surefire-plugin</artifactId>
                <version>3.5.4</version>
            </plugin>

        </plugins>
```

# Step 18: Write Your First Selenium Test

Replace the class with:

```java
package com.qmstesting.tests;

import org.openqa.selenium.By;
import org.openqa.selenium.WebDriver;
import org.openqa.selenium.WebElement;
import org.openqa.selenium.chrome.ChromeDriver;
import org.testng.Assert;
import org.testng.annotations.AfterMethod;
import org.testng.annotations.BeforeMethod;
import org.testng.annotations.Test;

public class FirstSeleniumTest {

    private WebDriver driver;

    @BeforeMethod
    public void setUp() {

        driver = new ChromeDriver();

        driver.manage().window().maximize();
    }

    @Test
    public void submitWebFormTest() {

        driver.get(
            "https://www.selenium.dev/selenium/web/web-form.html"
        );

        WebElement textBox =
                driver.findElement(By.name("my-text"));

        WebElement submitButton =
                driver.findElement(By.cssSelector("button"));

        textBox.sendKeys("Selenium");

        submitButton.click();

        WebElement message =
                driver.findElement(By.id("message"));

        Assert.assertEquals(
            message.getText(),
            "Received!"
        );
    }

    @AfterMethod
    public void tearDown() {

        if (driver != null) {
            driver.quit();
        }
    }
}
```

Save the file.

You have now created your first Selenium + TestNG automated test.

# The @BeforeMethod Annotation

```java

public void setUp() {
```

`@BeforeMethod` is a TestNG annotation.

It tells TestNG:

> Run this method before every `@Test` method.

Our setup method creates Chrome:



# The @Test Annotation

```java
@Test
public void submitWebFormTest() {
```

`@Test` tells TestNG that the method is a test.

TestNG discovers and executes methods marked with this annotation.

Good test names describe the behaviour being tested.

For example:

```java
validUserCanLogIn()
```

is better than:

```java
test1()
```

```java
Assert.assertEquals(
    message.getText(),
    "Received!"
);
```

This is an **assertion**.

Assertions are one of the most important concepts in test automation.

The first value is the actual value returned by the application:

```java
message.getText()
```

The second value is what we expect:

```text
Received!
```

The TestNG syntax is:

```java
Assert.assertEquals(actual, expected);
```

If:

```text
Actual = Received!
Expected = Received!
```

the assertion passes.

If the values differ, TestNG marks the test as failed.

---

# Why Assertions Are Important

Suppose Selenium successfully:

* opens a webpage;
* enters a username;
* enters a password;
* clicks Login; and
* closes the browser.

That does not necessarily prove that login worked.

The test should verify something.

For example:

```java
Assert.assertEquals(
    driver.getTitle(),
    "Dashboard"
);
```

or:

```java
Assert.assertTrue(
    logoutButton.isDisplayed()
);
```

Automation should **verify application behaviour**, not merely perform actions.

---

# The @AfterMethod Annotation

```java
@AfterMethod
public void tearDown() {
```

TestNG runs a method marked with `@AfterMethod` after every test method.

Our cleanup method contains:

```java
if (driver != null) {
    driver.quit();
}
```

`driver.quit()`:

* closes the browser;
* closes all browser windows associated with the session; and
* ends the WebDriver session.

Using cleanup code prevents browser processes from remaining open after your tests finish.

---

# TestNG Lifecycle Annotations

TestNG provides several useful annotations.

| Annotation      | Purpose                                |
| :-------------- | :------------------------------------- |
| `@Test`         | Defines a test                         |
| `@BeforeMethod` | Runs before every test method          |
| `@AfterMethod`  | Runs after every test method           |
| `@BeforeClass`  | Runs before tests in a class           |
| `@AfterClass`   | Runs after tests in a class            |
| `@BeforeTest`   | Runs before a TestNG `<test>`          |
| `@AfterTest`    | Runs after a TestNG `<test>`           |
| `@BeforeSuite`  | Runs before the entire suite           |
| `@AfterSuite`   | Runs after the entire suite            |
| `@DataProvider` | Supplies multiple sets of test data    |
| `@Parameters`   | Receives values from XML configuration |

For normal browser-test setup and cleanup, beginners will frequently use:

```java
@BeforeMethod
```

and:

```java
@AfterMethod
```

# Step 21: Understanding Selenium Manager

One of the biggest improvements in modern Selenium is **Selenium Manager**.

In older Selenium versions, Chrome automation usually required testers to:

1. determine the installed Chrome version;
2. locate a compatible ChromeDriver;
3. download ChromeDriver;
4. extract `chromedriver.exe`;
5. store it somewhere on the computer;
6. add the directory to `PATH` or specify it in Java;


1. detect the browser;
2. determine the required browser driver;
3. obtain the appropriate driver;
4. cache the driver locally; and
5. allow Selenium to start the browser.

You normally do **not** need to manually download ChromeDriver.

Afterward, Selenium can normally reuse the cached driver.

A corporate environment can sometimes prevent Selenium Manager from downloading a driver because of:

* firewall restrictions;
* proxy configuration;
* VPN restrictions;
* antivirus software;
* endpoint security; or
* Internet access restrictions.

If Selenium Manager reports an error, read the error message carefully before manually downloading browser drivers.

# Step 24: Learn Selenium Locators

The next major Selenium skill to learn is **locators**.

Before Selenium can interact with an element, Selenium must find it.

Consider this HTML:

```html
<input
    id="username"
    name="username"
    type="text"
    class="login-field">
```

Selenium can potentially locate this element several ways.

---

# Locate by ID

```java
driver.findElement(
    By.id("username")
);
```

A unique and stable HTML ID is often an excellent locator.

---

# Locate by Name

```java
driver.findElement(
    By.name("username")
);
```

---

# Locate by CSS Selector

Using the ID:

```java
driver.findElement(
    By.cssSelector("#username")
);
```

Using the `name` attribute:

```java
driver.findElement(
    By.cssSelector("input[name='username']")
);
```

CSS selectors are extremely useful and worth learning.

---

# Locate by Link Text

Consider:

```html
<a href="/contact">Contact Us</a>
```

You could locate this link using:

```java
driver.findElement(
    By.linkText("Contact Us")
);
```

---

# Locate by Partial Link Text

You could also use:

```java
driver.findElement(
    By.partialLinkText("Contact")
);
```

---

# Locate by XPath

For example:

```java
driver.findElement(
    By.xpath("//input[@id='username']")
);
```

XPath is very powerful.

However, beginners should avoid blindly copying huge XPath expressions generated by browser developer tools.

A locator such as:

```text
/html/body/div[2]/div/div[3]/form/div[2]/input
```

is often fragile.

Small changes to the page structure can break it.

---

# Choosing Good Selenium Locators

Good Selenium locators should ideally be:

* unique;
* stable;
* readable;
* easy to maintain; and
* resistant to visual layout changes.

Examples include:

```java
By.id("username")
```

or:

```java
By.cssSelector(
    "[data-testid='login-button']"
)
```

When possible, avoid locators based entirely on element position or complicated page structure.

# Step 27: Avoid Thread.sleep() for Normal Synchronization

Many beginner Selenium examples contain:

```java
Thread.sleep(5000);
```

This simply pauses Java for five seconds.

Fixed waits are sometimes useful while troubleshooting or demonstrating something, but they are generally a poor way to synchronize real Selenium tests.

Web applications are asynchronous.

An element might become available after:

```text
300 milliseconds
```

or:

```text
2 seconds
```

or:

```text
8 seconds
```

A five-second sleep can therefore be:

* unnecessarily long; or
* not long enough.

Modern Selenium tests should usually wait for a **specific condition**.

---

# Step 28: Use Explicit Waits

Selenium provides:

```java
WebDriverWait
```

and:

```java
ExpectedConditions
```

For example, import:

```java
import java.time.Duration;

import org.openqa.selenium.support.ui.ExpectedConditions;
import org.openqa.selenium.support.ui.WebDriverWait;
```

Create the wait:

```java
WebDriverWait wait =
        new WebDriverWait(
            driver,
            Duration.ofSeconds(10)
        );
```

Then wait for an element:

```java
WebElement message =
        wait.until(
            ExpectedConditions
                .visibilityOfElementLocated(
                    By.id("message")
                )
        );
```

This means:

> Wait up to 10 seconds for the element to become visible.

If the element appears after one second, Selenium continues immediately.

It does not automatically wait the entire ten seconds.

This is usually much more efficient than:

```java
Thread.sleep(10000);
```

# Step 29: Improve the First Test with Explicit Waits

Let's create a better version of our original test.

```java
package com.qmstesting.tests;

import java.time.Duration;

import org.openqa.selenium.By;
import org.openqa.selenium.WebDriver;
import org.openqa.selenium.WebElement;
import org.openqa.selenium.chrome.ChromeDriver;
import org.openqa.selenium.support.ui.ExpectedConditions;
import org.openqa.selenium.support.ui.WebDriverWait;
import org.testng.Assert;
import org.testng.annotations.AfterMethod;
import org.testng.annotations.BeforeMethod;
import org.testng.annotations.Test;

public class WebFormTest {

    private WebDriver driver;
    private WebDriverWait wait;

    @BeforeMethod
    public void setUp() {

        driver = new ChromeDriver();

        wait = new WebDriverWait(
            driver,
            Duration.ofSeconds(10)
        );

        driver.manage().window().maximize();
    }

    @Test
    public void userCanSubmitWebForm() {

        // Arrange
        driver.get(
            "https://www.selenium.dev/selenium/web/web-form.html"
        );

        WebElement textBox =
                wait.until(
                    ExpectedConditions
                        .visibilityOfElementLocated(
                            By.name("my-text")
                        )
                );

        // Act
        textBox.sendKeys("Selenium");

        driver.findElement(
            By.cssSelector("button")
        ).click();

        // Assert
        WebElement message =
                wait.until(
                    ExpectedConditions
                        .visibilityOfElementLocated(
                            By.id("message")
                        )
                );

        Assert.assertEquals(
            message.getText(),
            "Received!"
        );
    }

    @AfterMethod
    public void tearDown() {

        if (driver != null) {
            driver.quit();
        }
    }
}
```

This test demonstrates another useful testing structure:

```text
Arrange
Act
Assert
```

---

# Arrange

Prepare the application and test conditions.

For example:

```java
driver.get(
    "https://www.selenium.dev/selenium/web/web-form.html"
);
```

---

# Act

Perform the behaviour being tested.

For example:

```java
textBox.sendKeys("Selenium");

submitButton.click();
```

---

# Assert

Verify the result.

For example:

```java
Assert.assertEquals(
    message.getText(),
    "Received!"
);
```

# Step 32: Create Multiple TestNG Tests

One advantage of TestNG is that one class can contain multiple tests.

For example:

```java
@Test
public void pageTitleShouldBeCorrect() {

    driver.get(
        "https://www.selenium.dev/selenium/web/web-form.html"

    Assert.assertTrue(
        driver.getTitle().contains("Web form")
```

and:

```java
@Test
public void formSubmissionShouldDisplayMessage() {

    driver.findElement(
        By.name("my-text")

        driver.findElement(
            By.id("message")

    );

```

Because the class uses:

```java
@BeforeMethod
```

TestNG creates a new browser session before each test.

Because the class uses:

```java
@AfterMethod
```

TestNG closes the browser after each test.

This helps keep tests independent.

# assertEquals()

# Step 34: Verify That Your Test Can Fail

A good automation tester should verify that a new test can recognize incorrect behaviour.

Temporarily change:

```java
Assert.assertEquals(
    message.getText(),
    "Received!"
);
```

to:

```java
Assert.assertEquals(
    message.getText(),
    "Something Else"
```

TestNG should mark the test as failed.

Restore the correct assertion afterward.

This simple exercise demonstrates an important principle:

> A test that cannot fail when the result is incorrect is not providing meaningful protection.

# Step 38: Data-Driven Testing with @DataProvider

TestNG's `@DataProvider` is especially useful for Selenium testing.

Suppose you want to test a login page with several usernames and passwords.

You could create:

```java
@DataProvider(name = "loginData")
public Object[][] loginData() {

    return new Object[][] {

        {"user1", "password1"},
        {"user2", "password2"},
        {"user3", "password3"}

```

Then use that data in a test:

```java
@Test(dataProvider = "loginData")

        String username,
        String password) {

        "Testing user: " + username
    );
}
```

TestNG executes the test once for every data row.

That means this single test method executes three times.

* CSV files;
* JSON files;
* Excel files;
* databases;
* APIs; or
* other data sources.

# Step 40: Common Selenium Errors

Every Selenium tester eventually encounters errors.

Understanding common exceptions will make troubleshooting much easier.

---

# NoSuchElementException

Example:

```text
org.openqa.selenium.NoSuchElementException
```

This means Selenium could not locate an element.

Possible causes include:

* incorrect locator;
* webpage changed;
* element has not loaded;
* element is inside an iframe;
* Selenium is on the wrong page;
* element is in another browser window; or
* dynamic application code replaced the element.

First inspect the HTML again using browser developer tools.

---

# TimeoutException

This commonly occurs when using explicit waits.

For example:

```java
wait.until(
    ExpectedConditions
        .visibilityOfElementLocated(
            By.id("message")
        )
);
```

If the expected condition never occurs within the timeout, Selenium throws a timeout exception.

Check whether:

* the locator is correct;
* the page loaded successfully;
* the expected action occurred;
* another element is blocking the page; or
* your assumption about the application behaviour is incorrect.

---

# ElementClickInterceptedException

This usually means Selenium found the target element but something else blocked the click.

Common causes include:

* cookie banners;
* modal windows;
* advertisements;
* loading overlays;
* pop-ups; and
* sticky navigation bars.

---

# StaleElementReferenceException

Modern web applications frequently update the DOM dynamically.

Suppose Selenium stores:

```java
WebElement button =
        driver.findElement(
            By.id("submit")
        );
```

The page then redraws that button.

The original Selenium reference may no longer refer to the current element.

This can cause:

```text
StaleElementReferenceException
```

You may need to locate the element again.

# Selenium and TestNG Best Practices for Beginners

Developing good habits early will make your test suite much easier to maintain.

---

# Always Close the Browser

Use cleanup code such as:

```java
@AfterMethod
public void tearDown() {

    if (driver != null) {
        driver.quit();
    }
}
```

---

# Always Verify Something

Do not create automation that only performs actions.

Include meaningful assertions.

For example:

```java
Assert.assertEquals(
    driver.getTitle(),
    "Dashboard"
);
```

---

# Prefer Stable Locators

Avoid locators that depend heavily on visual position.

Prefer attributes intended to remain stable.

---

# Avoid Excessive Thread.sleep()

Prefer explicit waits based on the application state.

---

# Give Tests Meaningful Names

Better:

```java
public void validUserCanLogIn()
```

Less useful:

```java
public void test1()
```

The test name should communicate what behaviour is being verified.

---

# Keep Tests Independent

Where possible, each test should prepare the conditions it needs.

Avoid designs where:

```text
Test 2 requires Test 1
Test 3 requires Test 2
Test 4 requires Test 3
```

If Test 1 fails, the entire suite can become unusable.

Independent tests are generally easier to:

* rerun;
* debug;
* parallelize; and
* maintain.

---

# Keep One Clear Purpose Per Test

A test should have a clear reason to exist.

For example:

```text
Valid user can log in
```

is clearer than one enormous test that:

* logs in;
* edits the user profile;
* creates an order;
* cancels the order;
* changes the password;
* logs out; and
* performs ten unrelated assertions.

Smaller focused tests are usually easier to understand.

---

# Read Error Messages Carefully

When a Selenium test fails, avoid randomly changing the code.

Ask:

1. Which line failed?
2. What exception occurred?
3. What element was Selenium trying to find?
4. What did the test expect?
5. What did the application actually display?
6. Did the page finish loading?
7. Was another element blocking the action?
8. Did the application's HTML change?

Debugging is a major part of automation testing.

# Frequently Asked Questions

## Is Java still suitable for Selenium in 2026?

Yes.

## Why use TestNG instead of JUnit?

Both are capable Java testing frameworks.

TestNG is particularly attractive for Selenium projects because it provides convenient built-in support for:

For a Selenium-focused testing tutorial, TestNG provides a natural progression toward larger automation frameworks.

## Is TestNG part of Selenium?

No.

Selenium and TestNG are separate projects.

Selenium controls the browser.

TestNG organizes and executes your tests.

Maven allows them to be used together easily.

No.

* maintain driver versions; and

A modern Selenium project instead uses:

```text
Locate Elements
```
