## Introduction

If you're planning to automate browser testing with **Selenium WebDriver and Java**, IntelliJ IDEA provides an excellent development environment for building, running, debugging, and maintaining your automation tests.

IntelliJ IDEA includes features such as:

* Intelligent Java code completion
* Real-time error detection
* Integrated debugging
* Maven and Gradle support
* Git integration
* Built-in test execution
* Terminal access
* Project dependency management

A properly configured local Selenium project can also be moved much more easily into a **CI/CD environment such as Azure DevOps**.

In this 2026 guide, you'll learn how to:

1. Install IntelliJ IDEA
2. Install and configure a Java Development Kit (JDK)
3. Create a Maven project
4. Add Selenium WebDriver
5. Run your first Selenium test
6. Add TestNG
7. Run Selenium tests with Maven
8. Prepare the project for Azure DevOps
9. Configure Chrome for CI/CD execution

By the end, you'll have a working Selenium WebDriver project that can run locally and provides a solid foundation for a larger automation framework.

## What Has Changed in 2026?

If you've followed older Selenium tutorials, you may notice several important differences.

### IntelliJ IDEA Is Now One Product

JetBrains previously provided separate **Community** and **Ultimate** editions of IntelliJ IDEA.

Beginning with IntelliJ IDEA 2025.3, JetBrains moved to a **single unified IntelliJ IDEA distribution**.

You now download IntelliJ IDEA once. The core Java development functionality is free, while additional professional features are available through an Ultimate subscription.

For Selenium automation with Java, the free functionality is sufficient for everything covered in this tutorial.

### You Usually Don't Need to Download ChromeDriver

Older Selenium tutorials commonly required you to:

1. Determine your Chrome version.
2. Download the corresponding ChromeDriver.
3. Store ChromeDriver somewhere on your computer.
4. Configure the driver path in Java.

For example:

```java
System.setProperty(
    "webdriver.chrome.driver",
    "C:\\drivers\\chromedriver.exe"
);
```

For most users, **this is no longer necessary**.

Modern Selenium includes **Selenium Manager**, which can automatically determine the browser version, locate or download the appropriate driver, and cache it for future use.

This means a modern Selenium test can simply use:

```java
WebDriver driver = new ChromeDriver();
```

Selenium handles the driver management automatically.

# 7. Create Your First Selenium Test

Before introducing a testing framework, let's confirm that Selenium can successfully launch a browser.

Create a package under:

```text
src/test/java
```

Call it:

```text
tests
```

Inside the package, create a Java class called:

```text
FirstTest
```

Add the following code:

```java
package tests;

import org.openqa.selenium.WebDriver;
import org.openqa.selenium.chrome.ChromeDriver;

public class FirstTest {

    public static void main(String[] args) {

        WebDriver driver = new ChromeDriver();

        try {
            driver.get("https://www.example.com");

            System.out.println(
                "Page title: " + driver.getTitle()
            );

        } finally {
            driver.quit();
        }
    }
}
```

Notice what is **not** included:

```java
System.setProperty("webdriver.chrome.driver", "...");
```

You normally don't need it anymore.

# 9. How Selenium Manager Works

When Selenium encounters:

```java
new ChromeDriver();
```

it needs a compatible ChromeDriver executable.

If an appropriate driver isn't already available, **Selenium Manager** can handle the process automatically.

It can:

1. Detect the installed browser.
2. Determine the browser version.
3. Determine the compatible driver version.
4. Download the driver if required.
5. Cache the driver locally.
6. Supply the driver to Selenium.

Selenium Manager supports browser and driver management for major browsers including:

* Google Chrome
* Mozilla Firefox
* Microsoft Edge

This significantly simplifies Selenium setup compared with older versions.

### Internet Access

The first time Selenium Manager needs a particular driver, it may require internet access to retrieve it.

This is important in:

* Corporate networks
* Proxy-controlled environments
* Restricted build agents
* CI/CD environments

If your organization's firewall prevents Selenium Manager from reaching the necessary endpoints, additional proxy or driver configuration may be required.

# 11. Create a TestNG Selenium Test

Create another Java class under:

```text
src/test/java/tests
```

Call it:

```text
ExampleTest.java
```

Add:

```java
package tests;

import org.openqa.selenium.WebDriver;
import org.openqa.selenium.chrome.ChromeDriver;
import org.testng.Assert;
import org.testng.annotations.AfterMethod;
import org.testng.annotations.BeforeMethod;
import org.testng.annotations.Test;

public class ExampleTest {

    private WebDriver driver;

    @BeforeMethod
    public void setUp() {
        driver = new ChromeDriver();
    }

    @Test
    public void verifyExampleDomainTitle() {

        driver.get("https://www.example.com");

        String actualTitle = driver.getTitle();

        Assert.assertEquals(
            actualTitle,
            "Example Domain"
        );
    }

    @AfterMethod
    public void tearDown() {

        if (driver != null) {
            driver.quit();
        }
    }
}
```

This is already much closer to a real automated test.

---

# 12. Understanding the TestNG Annotations

### `@BeforeMethod`

```java
@BeforeMethod
public void setUp()
```

Runs before each test method.

In this example, it creates the browser session.

### `@Test`

```java
@Test
public void verifyExampleDomainTitle()
```

Identifies the method as a TestNG test.

### `@AfterMethod`

```java
@AfterMethod
public void tearDown()
```

Runs after each test.

It closes the browser even when the test fails.

This is important because poorly managed Selenium tests can otherwise leave multiple browser processes running.

# 16. Create a TestNG Suite

Create:

```text
testng.xml
```

in the project root.

For example:

```xml
<?xml version="1.0" encoding="UTF-8"?>

<!DOCTYPE suite SYSTEM "https://testng.org/testng-1.0.dtd">

<suite name="Selenium Test Suite">

    <test name="Example Tests">

        <classes>

            <class name="tests.ExampleTest"/>

        </classes>

    </test>

</suite>
```

The package name is important.

Because our test class contains:

```java
package tests;
```

the TestNG configuration uses:

```xml
<class name="tests.ExampleTest"/>
```

# 17. Prepare Selenium for Azure DevOps

Local browsers normally run with a visible window.

CI/CD agents are different.

Your Selenium tests should generally support **headless browser execution**.

Headless mode runs Chrome without displaying its normal browser window.

Modify the setup method:

```java
import org.openqa.selenium.chrome.ChromeOptions;
```

Then:

```java
@BeforeMethod
public void setUp() {

    ChromeOptions options = new ChromeOptions();

    options.addArguments("--headless=new");
    options.addArguments("--window-size=1920,1080");

    driver = new ChromeDriver(options);
}
```

Now the browser can run without displaying a graphical window.

---

# 18. Make Headless Mode Configurable

Running headless locally isn't always desirable because seeing the browser is useful while developing and debugging.

A better approach is to make headless mode configurable.

```java
@BeforeMethod
public void setUp() {

    ChromeOptions options = new ChromeOptions();

    String headless =
            System.getProperty("headless", "false");

    if (Boolean.parseBoolean(headless)) {

        options.addArguments("--headless=new");
        options.addArguments("--window-size=1920,1080");
    }

    driver = new ChromeDriver(options);
}
```

Now you can run normally with:

```bash
mvn clean test
```

or headlessly with:

```bash
mvn clean test -Dheadless=true
```

This is very useful for CI/CD.

# 21. Create an Azure DevOps Pipeline

Once the project is stored in an Azure DevOps repository or another repository connected to Azure Pipelines, create:

```text
azure-pipelines.yml
```

A simple starting pipeline could look like:

```yaml
trigger:
- main

pool:
  vmImage: 'ubuntu-latest'

steps:

- checkout: self

- script: |
    java -version
    mvn -version
  displayName: 'Display Java and Maven Versions'

- script: |
    mvn -B clean test -Dheadless=true
  displayName: 'Run Selenium Tests'

- task: PublishTestResults@2
  condition: succeededOrFailed()
  inputs:
    testResultsFormat: 'JUnit'
    testResultsFiles: '**/surefire-reports/TEST-*.xml'
    testRunTitle: 'Selenium Test Results'
```

This pipeline:

1. Creates a Microsoft-hosted Ubuntu agent.
2. Checks out your repository.
3. Displays the installed Java and Maven versions.
4. Runs the Selenium tests.
5. Publishes the Maven Surefire test results to Azure DevOps.

# 22. Why Use `ubuntu-latest`?

Microsoft provides hosted agents that already contain many common development tools.

As of 2026:

```yaml
vmImage: 'ubuntu-latest'
```

maps to a supported Ubuntu Microsoft-hosted image.

Using Microsoft-hosted agents is convenient for beginner automation projects because you don't need to maintain your own build server.

However, hosted agent software changes over time.

For production pipelines, you may eventually prefer to specify an exact supported image rather than relying indefinitely on:

```yaml
ubuntu-latest
```

This can make pipeline environments more predictable.

# 24. Troubleshooting Common Problems

## Problem: `mvn` Is Not Recognized

If you receive:

```text
'mvn' is not recognized
```

Maven may not be installed or available on your PATH.

You can:

* Install Maven separately
* Configure Maven in your PATH
* Use the Maven installation available through IntelliJ
* Use Maven Wrapper in more advanced projects

Check with:

```bash
mvn -version
```

---

## Problem: Java Version Is Incorrect

Check your Java installation:

```bash
java -version
```

And Maven:

```bash
mvn -version
```

Make sure Maven is using the intended JDK.

You can also verify IntelliJ under:

**File → Project Structure → Project SDK**

---

## Problem: Selenium Cannot Download a Driver

Selenium Manager may require access to browser-vendor download services.

Corporate environments may block this through:

* Firewalls
* Proxy servers
* Network security policies

If Selenium Manager works on your home computer but fails on a corporate network, network restrictions may be the cause.

---

## Problem: Browser Opens and Immediately Closes

That may be completely normal.

If your code ends with:

```java
driver.quit();
```

Selenium closes the browser when the test completes.

When debugging, add a breakpoint in IntelliJ rather than removing proper browser cleanup from production tests.

---

## Problem: Tests Work Locally but Fail in CI

Check for differences such as:

* Different Java versions
* Different browser versions
* Missing environment variables
* Hard-coded file paths
* Case-sensitive filenames on Linux
* Browser window-size differences
* Headless rendering differences
* Network restrictions
* Missing test data
* Secrets stored only on your local machine

A test that depends on something installed manually on your computer is less portable than one whose dependencies are managed by Maven and configuration.

# 26. Where to Go Next

Once this basic Selenium setup works, you can gradually add more advanced automation concepts.

## Page Object Model

Move page-specific locators and actions into page classes.

For example:

```text
LoginPage
HomePage
SearchPage
CheckoutPage
```

This makes tests easier to maintain.

---

## Explicit Waits

Real web applications load dynamically.

Instead of using:

```java
Thread.sleep(5000);
```

learn to use Selenium's explicit waits.

For example:

```java
WebDriverWait wait =
        new WebDriverWait(driver, Duration.ofSeconds(10));
```

Explicit waits make tests faster and more reliable.

---

## Screenshots on Failure

Configure your framework to automatically capture screenshots when a test fails.

These screenshots can later be stored as Azure DevOps pipeline artifacts.

---

## Logging

Consider adding a logging framework such as:

* SLF4J
* Log4j 2

Logging becomes increasingly useful when diagnosing failures in CI/CD environments.

---

## Data-Driven Testing

TestNG provides `@DataProvider`, which allows the same test to run using different sets of data.

For example:

```java
@DataProvider(name = "loginData")
public Object[][] loginData() {

    return new Object[][] {
        {"user1", "password1"},
        {"user2", "password2"}
    };
}
```

---

## Cross-Browser Testing

Once your Chrome tests are stable, you can expand the framework to run against:

* Chrome
* Firefox
* Edge

You can also explore remote testing services and Selenium Grid.

---

## Parallel Testing

Large regression suites can take a long time to execute sequentially.

TestNG and Selenium Grid can help execute multiple tests or browsers in parallel.

This can significantly reduce total test execution time.

---

# Final Thoughts

Setting up Selenium WebDriver in 2026 is considerably easier than it was a few years ago.

The biggest improvement for beginners is **Selenium Manager**.

Instead of manually downloading ChromeDriver, matching its version to Chrome, configuring system properties, and repeating the process whenever Chrome updates, Selenium can now handle most driver management automatically.

Using a combination of:

```text
IntelliJ IDEA
        ↓
Java JDK
        ↓
Maven
        ↓
Selenium WebDriver
        ↓
TestNG
        ↓
Git
        ↓
Azure DevOps
```

provides a practical foundation for modern Java browser automation.

The most important thing at this stage isn't building a complicated automation framework immediately.

Start with one test.

Make sure it runs from IntelliJ.

Then make sure it runs using:

```bash
mvn clean test
```

Next, make it run headlessly:

```bash
mvn clean test -Dheadless=true
```

Finally, run exactly the same project in your Azure DevOps pipeline.

Once that workflow is reliable, you can begin adding page objects, reusable utilities, reporting, screenshots, parallel execution, cross-browser testing, and more advanced CI/CD capabilities.

A simple Selenium project that runs reliably both locally and in CI/CD is a much better foundation than a complicated framework that is difficult to maintain.
